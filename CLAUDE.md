# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity 6.3 (`6000.3.11f1`, URP 2D) prototype: a turn-based arithmetic-combat game. Libraries: TextMeshPro, Lean Touch, DOTween, UniTask, Zenject. Active working scene: `Assets/Scenes/TestScene2.unity`. `PROJECT_HANDOFF.md` has the full design notes, combat rules and a list of unimplemented features — read it before changing gameplay.

## Current direction

The design is moving from one fixed structure with a single enemy to a **branching board** with up to two enemy **lanes**, built from an **Encounter** (a board prefab + enemy queues). Operators become fixed board features instead of player-placed tokens; chains evaluate from the root outward and stop at the first empty slot; defense damage is spread proportionally as per-pilot wounds across a chain. **Start with the "Start here" section at the top of `PROJECT_HANDOFF.md`: it says where the work stopped, what is unverified in Unity and what comes next.** The full decided design, glossary (AP = in-battle Action Points, SP = meta Skill Points, Board, Encounter, chain, toll and bonus nodes), open questions and phased task plan are in `PROJECT_HANDOFF.md`. `ReferenceImageBrief.md` is the brief used to generate visual references. The code described under "Architecture" below is the legacy fixed-structure version that will be migrated.

Conventions agreed with the user:
- Composition over inheritance: small single-responsibility scripts, reusable where possible. Put game rules (board evaluation, defense wounds, AP) in pure C# classes without `MonoBehaviour` so they are unit-testable and reusable by the planned solver editor tool.
- Use the vocabulary from the handoff glossary (AP vs SP, Board, Encounter, lane, chain) in code and docs.
- `PilotAnimationView` (`Assets/Scripts/Views`) plays a pilot's Idle / Attack / Defeated **legacy clips** on a picture (the PilotSlot prefab's `Pilot` sprite, the CardView prefab's `Picture` image). Legacy clips cannot swap sprites, so they key a `SpriteFrames.Frame` number and `SpriteFrames` (`[ExecuteAlways]`, so clips preview in the Animation window) shows that frame on the object's SpriteRenderer or Image: one clip plays on board and card. Each pilot asset points to its **animation prefab** (`AnimationPrefab`: SpriteRenderer for previewing + Animation with the clips + SpriteFrames with the frames; in `Assets/Art/PilotAnimations/<pilot>`; upgraded copies use their `BasePilot`'s); the slot and card copy its frames and clips at runtime. Idle loops (in step with the clock), Attack plays once on an attack-chain hit or ability use then back to Idle, Defeated plays once and the picture darkens after it (the turn waits); a missing or empty clip is skipped. New pilots: *Tools > Fun Game > Create Pilot Animation Prefabs* (frames from the picture's sliced sheet, an Idle clip over all of them, empty Attack/Defeated clips). Its `ShouldPlay*`/`Start` block is throwaway test code.

## Build / test

There is no CLI build or lint. Development happens in the Unity Editor (open the project folder with 6000.3.11f1) — compile errors surface in the Editor console. Claude can drive the Editor through the MCP for Unity connection (compile, run tests, run menu items, create assets, play-test in Play mode); never do so while the user is in Play mode (check `EditorApplication.isPlaying` first). The tools and the agreed workflow are listed in the "Start here" section of `PROJECT_HANDOFF.md`. The `*.csproj` / `.sln` files at the root are generated by Unity; don't edit them.

The pure battle and board code (`Assets/Scripts/Board`, assembly `FunGame.Board`) has EditMode tests in `Assets/Tests/EditMode` (run them from Unity's Test Runner). They can also be built and run without Unity using the editor's own Roslyn and runtime.

`Tools/BalanceLab` is a console tool that plays encounters with simulated players and writes an HTML balance report (see its README). It is built by `Tools/BalanceLab/run-lab.bat` from the pure code in `Assets/Scripts/Board` (including `Board/Sim`), so keep that code free of UnityEngine types.

## Architecture (current code, legacy fixed structure)

Game code lives in `Assets/Scripts` (namespaces `Controllers`, `Views`, `Installers`, ...). Third-party code under `Assets/Plugins`, `Assets/CurvedTextMeshPro`, `Assets/TextMesh Pro` is vendored — don't modify it.

- **Controllers** (`Assets/Scripts/Controllers`) hold game state and rules: `PlayerController` (HP, hand setup), `EnemyController` (HP, `EnemyAction` list, sequential/random preview selection), `StructureController` (computes attack/defense from slot views, absorbs enemy damage), `TurnController` (`ResolveTurn()` orchestrates a full turn; wired to the Play Turn button's `OnClick`).
- **Views** (`Assets/Scripts/Views`) are MonoBehaviours for tokens and slots: pilots/operators (`PilotTokenView`, `OperationTokenView` over `TokenBaseView`), slots (`PilotSlotView`, `OperatorSlotView` over `TokenSlotBaseView`), and hands. `StructureController` subscribes to slot-change events and recomputes stats; `PilotSlotView` owns per-pilot runtime `ActiveDefenseValue`.
- **Data**: pilot/operator stats are ScriptableObjects (`Assets/Scripts/Configurations`, `PilotsLibrary`). Treat them as immutable — runtime damage mutates `ActiveDefenseValue` on the slot view, never the asset.
- **Wiring**: mostly `[SerializeField]` references assigned in the scene; Zenject is used minimally (`Installers/CombatInstaller` binds `PilotHandView`). Scene setup for new controllers is manual (see "Scene setup still needed" in the handoff), so adding a controller requires updating the scene/prefab too.
- **Turn resolution** is async: DOTween animations awaited via UniTask, with a guard preventing re-entry while a turn resolves. Damage drains defense pilots furthest → closest before hitting player HP.
- **Legacy/older prototypes**: `Assets/Cards` (card/deck/drag prototype, global namespace) and `Assets/Robot` are earlier experiments separate from the current pilot/structure system; `Assets/_Recovery` holds Unity scene recovery files.
